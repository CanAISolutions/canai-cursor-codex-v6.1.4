## 2. Codex Pillars, Enforcement, and Recovery Backbone

**Codex v6.1.4 Pillars:**
- **Security:** No silent failures, trust erosion, or unvalidated logic
- **Operational Resilience:** Fallbacks, chaos, and recovery are real, not simulated
- **Emotional UX Fidelity:** Every output, prompt, and fallback must pass the Emotional OS
- **Accessibility & Inclusion:** Multilingual, a11y, and edge-case coverage
- **Agent Enablement:** Agents must be testable, auditable, and emotionally intelligent

**Enforcement Protocols:**
- All tests must be Real System Bound (no unjustified mocks)
- Emotional volatility, agent trace, and fallback chains must be validated with live logic
- CI/CD gates block non-compliant tests and pillar violations
- All actions, blockers, and escalations are logged in `/cursor/auto-actions.log.md`
- Operator feedback and escalation protocol is always active
- **CI Enforcement Test:** `/cursor/tests/enforcement/ci-checklist-verification.test.ts` fails CI if any enforcement item is not complete. Output is machine-readable for audit and dashboard use.
- **Runtime Enforcement Guard:** `/cursor/runtime/enforceChecklistStatusGuard.ts` and `/cursor/runtime-hooks/enforce-checklist-guard.ts` are injected into all critical runtime flows (prompt, Make, schema mutation). If enforcement is incomplete, the system logs a `SchemaEvents` entry, flags the session as `blocked`, and triggers an emotionally intelligent fallback or graceful halt.
- **Drift Sentinel:** `/cursor/heartbeat/driftWatchdog.ts` logs all contract, schema, and version change events to `/cursor/system-intel/drift-trace-log.json`.
- **Universal Contract Registry:** `/cursor/contracts/universal-contract-registry.ts` logs all contract, field, and alias registrations. CI diff check blocks unregistered or missing contracts/fields.
- **Immutable Backup & Disaster Recovery:** Nightly Airtable → S3 backup, with weekly CI restore test. All restore events are logged and auditable.
- **Cost & Compliance Logging:** `/infra/airtable/tables/delivery-cost-logs.json` logs all ops with cost, token, and operational telemetry. Consent, deletion, and agent actions are logged in `/cursor/logs/AgentActions.json` and enforced by CI.
- **Rollback Mechanisms:** `rollback_airtable.sh` and `rollback_prompts.sh` restore from versioned backups, with all actions logged to `/cursor/system-intel/rollback-events.json`.

## Key Prompt Handlers and API Routing

This section provides an overview of the key prompt handlers within the CanAI ecosystem, detailing their functionality and how they interact with the APIs to fulfill prompt requests.

### 1. `openaiHandler.ts`
- **Functionality**: Handles GPT-4o prompt fulfillment for all CanAI product types. It routes structured input through the correct prompt builder and calls the GPT-4o model.
- **API Interaction**: Utilizes the OpenAI API to generate responses based on the composed prompts. It requires the `OPENAI_API_KEY` environment variable for authentication.
- **Error Handling**: Manages HTTP method validation and input validation, returning appropriate status codes for errors.

### 2. `prompt_handler.ts`
- **Functionality**: Acts as a safe fallback GPT fulfillment endpoint for manually testing or bypassing Make flows. It ensures compliance with Codex standards.
- **API Interaction**: Similar to `openaiHandler.ts`, it uses the OpenAI API to fulfill prompt requests. It includes an enforcement guard to ensure checklist compliance.
- **Error Handling**: Provides robust error handling with standardized error responses and logging for debugging.

### 3. `promptTypeRouter.ts`
- **Functionality**: Routes structured session input to the correct product prompt. It validates the `PromptType` and supports version switching.
- **API Interaction**: Works in conjunction with the prompt handlers to ensure the correct routing and processing of prompts.
- **Error Handling**: Throws errors for invalid or unsupported `PromptType` values, ensuring only valid prompts are processed.

### Overview of API Routing
- **Routing Logic**: The prompt handlers are designed to route structured input through the appropriate processing paths based on the `PromptType`. This ensures that each prompt is handled by the correct logic and template.
- **Integration with OpenAI**: The handlers integrate with the OpenAI API to generate responses, leveraging the capabilities of the GPT-4o model to fulfill prompt requests.
- **Error Management**: Comprehensive error handling is implemented across all handlers to ensure robustness and reliability in production environments.

This section aims to provide a clear understanding of the key prompt handlers and their role in the CanAI ecosystem, ensuring efficient and reliable prompt processing through the APIs.

## Core Product Deliveries: Key Components and Integration

This section outlines the critical components involved in delivering the 7 core products within the CanAI system, detailing their roles, integration, and contribution to the overall ecosystem.

### Key Components

1. **Prompt Files**
   - Each core product has a dedicated `.mcp.ts` file in the `prompts` directory, such as `business-plan.mcp.ts`, `social_content.mcp.ts`, etc.
   - These files define the logic and structure for each product's prompt, ensuring tailored processing and output.

2. **Prompt Type Router**
   - The `promptTypeRouter.ts` file routes structured session input to the correct product prompt.
   - It ensures that each prompt is processed according to its specific logic and requirements, supporting version switching and validation.

3. **Handlers**
   - The `openaiHandler.ts` and `prompt_handler.ts` files manage the interaction with the OpenAI API.
   - They fulfill prompt requests and ensure compliance with Codex standards, handling errors and logging for traceability.

4. **Validators**
   - The `promptValidator.ts` file provides validation schemas and helpers for prompt-related API operations.
   - It ensures data integrity and compliance with required standards, supporting robust error handling.

5. **Templates**
   - The `gpt-templates` directory contains templates used by the `composePrompt` function to generate GPT-ready prompts.
   - These templates are versioned and structured to support dynamic prompt composition.

6. **Logging and Auditing**
   - The `PromptLogs` directory and related logging mechanisms ensure that all prompt processing is traceable and auditable.
   - This supports system integrity, compliance, and continuous improvement through feedback loops.

### Integration and Workflow
- **Routing and Processing**: The prompt type router and handlers work together to ensure that each prompt is routed and processed correctly, leveraging the OpenAI API for fulfillment.
- **Validation and Compliance**: Validators ensure that all inputs and outputs meet the required standards, supporting error handling and fallback mechanisms.
- **Template Utilization**: Templates provide the structure for prompt composition, enabling dynamic and context-aware responses.
- **Audit and Feedback**: Logging and auditing mechanisms provide traceability and support continuous improvement, ensuring system reliability and user trust.
