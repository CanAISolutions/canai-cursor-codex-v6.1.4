# 🔒 Authentication & Authorization Logic — API Router

## Purpose
Ensure all protected API endpoints enforce strict, predictable authentication and authorization, securing session integrity, operational continuity, emotional UX durability, and AI Copilot synchronization across all scaling phases.

---

## 1. Authentication Enforcement Rules

| Rule | Status |
|:---|:---|
| All non-public API routes require Bearer token authentication | ✅ Enforced |
| Healthcheck and system ping endpoints must bypass auth cleanly | ✅ Enforced |
| Tokens must be structurally validated before auth flow | ✅ Enforced |
| Expired tokens trigger refresh workflows if available | ✅ Enforced |
| Missing or invalid tokens yield emotionally safe fallback messages (no raw errors) | ✅ Enforced |

**Authentication Middleware (`requireAuth`) Behavior:**
- Extracts bearer token from `Authorization` header.
- Verifies structure, signature, and expiration.
- Attaches validated user payload to request object (`req.user`).

---

## 2. Authorization Enforcement Rules

| Rule | Status |
|:---|:---|
| Role-Based Access Control (RBAC) is mandatory for privileged routes | ✅ Enforced |
| Authorization only runs AFTER successful authentication | ✅ Enforced |
| Role permissions must be declared, versioned, and snapshot-tested | ✅ Enforced |

**Authorization Middleware (`requireRole`) Behavior:**
- Checks `req.user.role` against allowed roles per endpoint.
- Throws standardized 403 UX fallback if unauthorized.

**Standard Roles:**
- `user` — basic account access
- `admin` — elevated management privileges
- `system` — infrastructure/internal system-only access

---

## 3. Token Standards

| Claim | Requirement |
|:---|:---|
| `sub` | Unique user identifier |
| `role` | User role string |
| `exp` | Expiration timestamp (Unix Epoch) |

**Access Token Characteristics:**
- Short lifespan (e.g., 15–60 minutes)
- Stateless, verifiable

**Refresh Token Characteristics:**
- Longer lifespan (e.g., 7–30 days)
- Stored server-side or with secure HttpOnly cookies
- Subject to key rotation policies

**JWT Access Token Example:**
```json
{
  "sub": "user_12345",
  "role": "user",
  "exp": 1716242357
}
```

---

## 4. Failure UX Standards

| Failure Scenario | Standard Response |
|:---|:---|
| Missing Token | HTTP 401 with "Authentication required to continue." |
| Invalid Token | HTTP 401 with "Invalid or expired session. Please log in again." |
| Unauthorized Role | HTTP 403 with "You do not have permission to perform this action." |

**Error Response Format (Snapshot Safe):**
```json
{
  "success": false,
  "error": {
    "code": "AUTH_REQUIRED",
    "message": "Authentication is required to access this resource."
  }
}
```

---

## 5. Middleware Call Chain (Mandatory)

Every protected route must implement middleware in this order:
1. **Input Validation** — Validate request payload structure
2. **Authentication (`requireAuth`)** — Verify and attach user
3. **Authorization (`requireRole`)** — Validate role permissions
4. **Rate Limiting (optional)** — Per-user throttling if applicable
5. **Business Logic Execution** — Perform protected action

## 6. Copilot Affordances Embedded

| Affordance | Purpose |
|:---|:---|
