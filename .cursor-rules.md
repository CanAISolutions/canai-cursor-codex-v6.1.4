# Cursor Rules for CanAI Project

## 1. Introduction
This policy governs AI-assisted development for the CanAI project, ensuring disciplined, high-quality work with a focus on Supabase integration and Circuit Breaker patterns.

### 1.1 Actors
- **User**: Defines requirements, prioritizes tasks, approves changes, and is accountable for all code.
- **AI_Agent**: Executes User instructions per tasks, adhering to this policy.

### 1.2 Compliance
- All tasks must be explicitly defined and approved by the User.
- All code changes must be associated with a task.

## 2. Fundamental Principles
1. **Task-Driven Development**: No code changes without an approved task.
2. **User Authority**: The User decides scope and design of all work.
3. **User Responsibility**: The User is accountable for all code changes.
4. **No Unapproved Changes**: Changes outside a task’s scope are prohibited. If the User requests an unassociated change, the AI_Agent must discuss task creation first.
5. **Task Granularity**: Tasks must be small, cohesive, and testable. Complex features (e.g., Circuit Breaker state machine) must be broken into smaller tasks.
6. **DRY (Don't Repeat Yourself)**: Define information once; reference elsewhere. Task details live in task files, referenced in summaries.
7. **Constants for Special Values**: Values used more than once (e.g., timeouts, retry counts) must be named constants (e.g., `const RESET_TIMEOUT = 30000;`).
8. **External Package Research**:
   - For external packages (e.g., Supabase), research official documentation first.
   - Create a guide file `<task_id>-<package>-guide.md` (e.g., `tasks/1-1-supabase-guide.md`) with API usage, date-stamp, and source links.
   - Example for Supabase: Document client initialization, auth flows, and error handling.
9. **Technical Documentation**: For tasks creating/modifying APIs or state machines (e.g., Circuit Breaker), document usage, states, transitions, and error handling in `docs/technical/`, linked from the task file.
10. **Scope Adherence**: No gold plating. Propose improvements as new tasks.

## 3. Task Management
### 3.1 Task Documentation
- **Location**: `docs/tasks/<TASK-ID>.md` (e.g., `docs/tasks/1-1.md`).
- **Required Sections**:
  - `# [TASK-ID] [Task-Name]`
  - `## Description`
  - `## Status History`
  - `## Requirements`
  - `## Implementation Plan`
  - `## Test Plan` (see Section 5)
  - `## Verification`
  - `## Files Modified`
- **Task Index**: `docs/tasks/index.md` lists all tasks in a table: `| Task ID | Name | Status | Description |`.

### 3.2 Task Workflow
- **Statuses**: Proposed, Agreed, InProgress, Review, Done, Blocked.
- **Transitions**:
  - `user_approves` (Proposed -> Agreed): Create task file, log in history.
  - `start_work` (Agreed -> InProgress): Create branch, log start time.
  - `submit_for_review` (InProgress -> Review): Run tests, notify User.
  - `approve` (Review -> Done): Merge changes, log completion.
  - `reject` (Review -> InProgress): Document feedback, resume work.
  - `mark_blocked` (InProgress -> Blocked): Document reason, notify User.
  - `unblock` (Blocked -> InProgress): Document resolution, resume work.
- **Status History**: Log all transitions in the task file: `| Timestamp | Event | From | To | Details | User |`.
- **Concurrency**: Multiple tasks can be InProgress if the User approves, to allow flexibility.

### 3.3 Version Control
- **Commit Message**: `<task_id> <task_description>` (e.g., `1-1 Add Supabase auth`).
- **On Done**: Run `git acp "<task_id> <task_description>"` to stage, commit, and push.

5. Circuit Breaker Implementation
5.1 State Machine Overview
The Circuit Breaker has three states (CLOSED, OPEN, HALF_OPEN), as per the diagram:

CLOSED: Normal operation, track success/failure, reset on success.
OPEN: Service down, fast-fail requests, wait for reset timeout.
HALF_OPEN: Test recovery, allow single test request, decide next state.
5.2 Implementation Rules
State Management:
Define states as an enum: enum CircuitBreakerState { CLOSED, OPEN, HALF_OPEN }.
Store state in a Supabase table circuit_breakers with columns: id, state, failure_count, last_failure_time, reset_timeout.
Example schema:
sql

Copy
CREATE TABLE circuit_breakers (
  id SERIAL PRIMARY KEY,
  state TEXT NOT NULL,
  failure_count INT DEFAULT 0,
  last_failure_time TIMESTAMP,
  reset_timeout INT DEFAULT 30000
);
Transitions:
CLOSED -> OPEN: On 3 consecutive failures, set state to OPEN, set reset_timeout.
OPEN -> HALF_OPEN: After reset_timeout expires, set state to HALF_OPEN.
HALF_OPEN -> CLOSED: On test request success, set state to CLOSED, reset failure_count.
HALF_OPEN -> OPEN: On test request failure, set state to OPEN, apply exponential backoff to reset_timeout.
Update the Supabase table on each transition.
Configuration:
Define constants: const MAX_FAILURES = 3;, const BASE_RESET_TIMEOUT = 30000;.
Use exponential backoff for retries: newTimeout = BASE_RESET_TIMEOUT * 2 ^ attempt.
Integration with Supabase:
Wrap Supabase requests in the Circuit Breaker.
Example:
ts

Copy
async function makeSupabaseRequest(query) {
  const breaker = await supabase.from('circuit_breakers').select('*').eq('id', 1).single();
  if (breaker.state === 'OPEN') throw new Error('Service unavailable');
  if (breaker.state === 'HALF_OPEN') {
    // Allow single test request
  }
  try {
    const result = await query();
    if (breaker.state === 'HALF_OPEN') {
      await supabase.from('circuit_breakers').update({ state: 'CLOSED', failure_count: 0 }).eq('id', 1);
    }
    return result;
  } catch (error) {
    await supabase.from('circuit_breakers').update({
      failure_count: breaker.failure_count + 1,
      last_failure_time: new Date(),
      state: breaker.failure_count + 1 >= MAX_FAILURES ? 'OPEN' : breaker.state
    }).eq('id', 1);
    throw error;
  }
}
Documentation:
Document the Circuit Breaker in docs/technical/circuit-breaker.md, including states, transitions, and Supabase integration.
5.3 Testing Circuit Breaker
Unit Tests:
Test state transitions in isolation (e.g., CLOSED -> OPEN after 3 failures).
Mock Supabase calls.
Integration Tests:
Test Circuit Breaker with real Supabase calls in a test environment.
Simulate failures (e.g., network issues) to trigger state changes.
E2E Tests:
Verify the full flow: normal operation, failure triggering OPEN, recovery to HALF_OPEN, and back to CLOSED.
Example: “Simulate 3 failed Supabase requests, verify fast-fail, then recover after timeout.”
6. Testing Strategy
Principles:
Risk-based: Focus testing on complex features (e.g., Circuit Breaker, Supabase real-time).
Test Pyramid: Unit tests for logic, integration tests for Supabase/Circuit Breaker, E2E for critical flows.
Automated: Automate all tests.
Task-Level Test Plans:
Every task must include a ## Test Plan section.
Simple tasks (e.g., constants): Verify compilation.
Complex tasks (e.g., Circuit Breaker): Define objectives, scenarios (success, failure, edge cases), and success criteria.
No task is “Done” until tests pass.
Dedicated E2E Task:
Create a task 1-E2E-Test to verify the overall Circuit Breaker and Supabase flow.
